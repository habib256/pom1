# POM1 UI architecture (Dear ImGui)

Docking, the renderer seam, interface zoom, the CRT stack, the editors and the
Bench — and the decision seams that were extracted out of `MainWindow` so the
largest layer in the tree could be tested at all.

Split out of [`CLAUDE.md`](../CLAUDE.md), which keeps the short version and
points here. Doc map → [`doc/README.md`](README.md).

---

- **Docking** (`MainWindow_Dock.cpp`) — POM1 builds against Dear ImGui's **`docking` branch**, pinned by the repo-root **`IMGUI_VERSION`** file (`<git tag> <IMGUI_VERSION_NUM floor>`) — bump it there and nowhere else. It used to be copy-pasted across the build; the count in this file said nine and the real number turned out to be eleven, which is the whole argument for a single source. CMake, `tools/ensure_imgui.sh` (used by `setup_pom1.sh`, `ci.yml`, `packaging/raspberrypi/install.sh` and the three packaging containers) and `setup_pom1.bat` all READ it. Only `release.yml` and `pi-borne.yml` still carry a literal, their `env:` blocks being parsed before any step can read a file — and `tools/check_imgui_pin.sh` (ctest **`imgui_pin_sync`**) scans every tracked file for a `vX.Y.Z-docking` literal that disagrees, so a twelfth site is caught the day it appears rather than at the next bump. `renderDockSpace()` submits one host window (`##POM1DockHost`, `NoBackground` + `NoBringToFrontOnFocus`) spanning the viewport minus the menu+toolbar band and the status band, hosting a single `DockSpace` with `PassthruCentralNode`; it **must run before the first dockable `Begin()`** of the frame — `render()` calls it straight after `renderToolbar()`. The three windows that frame it (`##Toolbar`, `##StatusBar`, `##ProfileChooser`) carry `ImGuiWindowFlags_NoDocking` so the workspace can never swallow its own borders. **Multi-viewport stays OFF** (no `ViewportsEnable`): WASM cannot do it at all and the hand-rolled Metal backend (`PomRenderer_Metal.mm` + its `CAMetalLayer` + the per-slot CRT stack) would need secondary-viewport support — two divergent paths for a marginal gain. The factory arrangement lives in `kDockLayout[]` (Apple-1 raster in the central node, card framebuffers + editors + Bench in a workspace node to its right, inspectors in a right column, consoles/printers/terminals in a bottom strip); anything absent from that table floats by design (tutorials, photos, About/Welcome, settings panels, transient file dialogs, and both Memory Map Bars — they own bespoke geometry persistence via `syncMemoryBarIniToDisk`). `buildDefaultDockLayout()` re-runs whenever `DockBuilderGetNode()` finds nothing: fresh profile, legacy pre-docking ini, or a preset switch (`applyMachineConfig`'s existing `ImGui::ClearIniSettings()` drops every node, and the incoming ini either restores its own or has none). Settings → Reset Windows Layout → **"Docking only"** forces a rebuild over an existing node via `wantDockLayoutRebuild`. Nothing else was needed for persistence: `SaveIniSettingsToDisk`/`LoadIniSettingsFromDisk` already round-trip `[Docking][Data]` into each `ini/imgui_preset_NN.ini`. `ini_defaults/*.ini` **do** carry a curated `[Docking][Data]` (hand-arranged per profile, promoted from a real session — regenerate one by rearranging the workspace, then copying `ini/imgui_preset_NN.ini` + `ini/preset_NN.size` over the `ini_defaults/` pair). So a shipped profile boots on ITS curated arrangement and `buildDefaultDockLayout()` is the fallback only: no seed, a legacy pre-docking ini, or Settings → Reset Windows Layout → "Docking only".
- **main_imgui.cpp** — GLFW + per-platform graphics backend (see **PomRenderer** below): OpenGL 3.2 Core / GLSL 150 on Linux + Windows (and legacy macOS via `POM1_RENDERER=opengl`), WebGL 2 / GLSL ES 300 on WASM, Metal on macOS by default. `GLFW_OPENGL_FORWARD_COMPAT` only on the macOS-GL fallback path; macOS-Metal uses `GLFW_CLIENT_API=GLFW_NO_API`. SIGINT/SIGTERM → `glfwSetWindowShouldClose(1)` so `--save-tape` flushes. **Adaptive UI refresh** (desktop only, `idle_throttle` in `ini/ui.settings`, Display Settings toggle): the loop drops to a ~5 Hz render floor when idle — full rate for 10 s at boot, 2 s after any GLFW event, and while `MainWindow::wantsContinuousRender()` (pending screen output, a card framebuffer that actually changed < 2 s ago (`lastCardFbChangeTime`, stamped by GEN2's diffed `render()` and the TMS/GT-6144 upload dirty-gates — a static title screen idles), status message, deferred-plug frames, a pending fullscreen screen-expand — deliberately NOT the CRT shader, which is on by default and whose only owned motion, the persistence trail, finishes fading at the idle floor). Frame-COUNTED logic in `render()` must either finish within the boot/input grace or appear in that predicate. **Card texture uploads are dirty-gated**: TMS9918 (288×216) + GT-6144 memcmp the fresh framebuffer against the last uploaded copy and skip `updateTexture` when identical (GEN2 already gated by `render()`'s return).
- **Interface zoom** (`applyUiTheme()` in `MainWindow_Presets.cpp`, ported from POM2's `Pom2Theme`) — ONE style apply scales colours, geometry and fonts together: the function **rebuilds the style from a default-constructed `ImGuiStyle`** every call, because `ImGuiStyle::ScaleAllSizes()` is *cumulative* (re-applying a zoom on a live style compounds the padding), then `ScaleAllSizes(uiScale_ * dpi)` + `FontScaleMain = uiScale_` / `FontScaleDpi = dpi` (1.92 dynamic fonts — no atlas rebuild, no backend texture refresh mid-session). `io.FontGlobalScale` is gone. Persisted as `ui_scale` in `ini/ui.settings` (old `hidpi_scale` migrates in); the DPI half is the monitor content scale, polled every frame by `syncUiDpiScale()` and gated by the "Auto (follow monitor DPI)" checkbox. **POM1's own chrome constants are NOT covered by `ScaleAllSizes`** — `kToolbarBandHeight` / `kStatusBarBandHeight` / the Apple-1 window pads live in `MainWindow_Internal.h`, authored at 100 %, and every use site multiplies them through `detail::uiPx()`; forget one and the dockspace (which reserves the same two bands) overlaps a toolbar whose contents grew. **The same rule covers every explicit widget size** — `ImGui::Button(label, ImVec2(w,h))`, `SetNextItemWidth`, `SameLine(0, spacing)`, window size constraints: the box is authored at 100 % but the glyph inside it is the live font, which the zoom *does* scale, so a raw literal clips its own icon (that is what cut the cassette deck's header icons past ~150 %) or breaks the button's proportions (`x1`/`x2` kept a raw 24 px height next to `uiPx(28,24)` neighbours). Prefer a floor over a fixed size (`max(authored × zoom, GetFontSize() × iconScale + 2×FramePadding.y)`) so an oversized font grows the box. **Portable widgets** (`CassetteDeck_ImGui`, the paint/sprite editors, Bench) must not include `MainWindow_Internal.h` for this: read the same factor from `ImGuiStyle` — `FontScaleMain × FontScaleDpi` is exactly `uiPx`'s multiplier, published by this function. A zoom change also queues a one-shot `ScaleWindowsInViewport` (`uiPendingWindowScale_`, applied at the top of the next `render()` like ImGui's own DPI path) so FLOATING windows follow; docked ones keep their share of the dockspace.
- **PomRenderer** (`src/PomRenderer.h` + `_GL.cpp` / `_Metal.mm` / `_Internal.h`) — opaque renderer seam. Public API: `createTexture` / `updateTexture` / `destroyTexture` / `asImTextureID` / `textureWidth` / `textureHeight` / `beginFrame` / `clear` / `renderDrawData` / `present` / `readBackbufferRGBA` / `initImGuiBackend` / `shutdownImGuiBackend`. Factory `pom1::makeRenderer(GLFWwindow*)` dispatches via `#if POM1_HAS_METAL`; `pom1::renderer()` exposes the singleton wired by `main_imgui.cpp` after window creation. Every texture site in the rest of the codebase (Screen_ImGui glyph atlas, HGR/TMS9918/GT6144 framebuffers, 10 photo textures in `MainWindow_Dialogs` — Help → Photos windows, incl. the **interactive Apple-1 keyboard** (`a-1_Keyboard.png`: `kKbdKeys[]` overlays one `InvisibleButton` per keycap, normalised rects validated against the photo; clicking queues the key through `EmulationController::queueKey`, with sticky one-shot SHIFT/CTRL latches, `CTRL+letter`→`toupper&0x1F` control codes, REPT re-send, and the red keycap → warm `reset()`), HGR/TMS Paint editor canvases via `Pom1HgrPaintHost`/`Pom1TmsPaintHost`) goes through this. The Metal backend wraps a `CAMetalLayer` on GLFW's NSWindow, BGRA8 drawables (`framebufferOnly = NO` so the screenshot blit can read them), `@autoreleasepool` per frame (compiled `-fno-objc-arc`; the patched `imgui_impl_metal.mm` next to it is `-fobjc-arc` to match upstream — ARC discipline is asymmetric). **Filter::Nearest on Metal**: `imgui_impl_metal` binds ONE sampler for the whole frame, so PomRenderer's per-texture `Filter::Nearest` contract needs a backend patch. CMake rewrites the upstream copy at configure time and compiles the patched copy — pixel-art framebuffers/glyphs/canvases stay crisp; photos + fonts also sample with nearest, which is visually invisible at integer zoom. Since **v1.92.8** upstream builds two `MTLSamplerState`s and exposes them as standard draw callbacks (`ImGuiPlatformIO::DrawCallback_SetSamplerNearest`), so the patch now flips the *linear* descriptor to nearest (`MTLSamplerMinMagFilterLinear`/`MTLSamplerMipFilterLinear` → `…Nearest`) instead of rewriting the old inline MSL `constexpr sampler` (that ≤ v1.92.7 replace is kept as a fallback). Both replaces are guarded: if neither matches, configure emits a **WARNING** rather than silently shipping blurry pixel art. Going per-image would mean threading `AddCallback()` through every texture draw site — deliberately not done. Screenshot path encodes the blit + presentDrawable on the same command buffer so the just-rendered frame is readable.
- **NativeFileDialog** (`src/NativeFileDialog.{h,cpp}` + `_Mac.mm`) — opens the OS's localised file picker for Load/Save Memory, Load/Save Tape, Load/Save Snapshot. Win32 `GetOpenFileNameW`/`GetSaveFileNameW` (links `comdlg32`), Cocoa `NSOpenPanel`/`NSSavePanel`, Linux probes `$PATH` for `zenity` then `kdialog` (forked, stdout-captured) on first call and caches the choice. WASM and Linux-without-zenity-or-kdialog fall back to the existing ImGui browser. **The Raspberry Pi defaults to the ImGui browser even when zenity exists** (`defaultEnabled()`): the kiosk session is a **bare X server** (no WM at all since the kiosk rework — POM1 goes fullscreen itself via `--fullscreen`) with no GTK/KDE desktop, so a forked picker cold-starts for seconds off the SD card and can land behind the fullscreen window. Detected from BOTH the native GLES tier (`POM1_GL_ES` — `-DPOM1_GLES=ON`, what `build_native_pi.sh` now uses by default) and a runtime `/proc/device-tree/model` probe, which still covers a `--desktop-gl` build. The Settings toggle overrides it and persists as `native_dialogs` in `ini/ui.settings`. **The fork must not park the render thread**: `runChildCapture()` polls the pipe and reaps with `WNOHANG`, calling a host pump (`NativeFileDialog::setWaitPump`, installed by `main_imgui.cpp` as `glfwPollEvents`) every few ms. A blocking `read`+`waitpid` there froze the GLFW loop for the entire life of the picker — nothing answered the compositor's `xdg_shell` ping and GNOME put up *"POM1 is not responding"* over a window that was only waiting for a file to be chosen (reported on the BBS flow, `File > Load Memory > software/NET/bbs.*.txt`, but every Load/Save shared it). The pump necessarily fires from **inside an ImGui frame** — the callers are menu handlers — so `main_imgui.cpp` raises `g_inNativeDialogPump` around the poll and the POM1 half of the key/char/drop callbacks is skipped for the duration: `handleGlfwKey` dispatches shortcuts, and a shortcut re-entering `applyMachineConfig`/`hardReset` underneath a live Load Memory is not a state anything there is prepared for (ImGui's own handlers still run — they only queue). With no pump installed the wait degrades to the old blocking form, which is what keeps the module standalone. Pinned by `native_file_dialog_smoke`.  Load Memory binary still pops a small ImGui "address only" follow-up since `.bin` files have no embedded address. Cassette deck's Load/Save buttons route through the same action methods so they pick up native too. **The portable HGR/TMS Paint editors and DevBench also route through native** — their host seams (`IHgrPaintHost`/`ITmsPaintHost`/`IBenchHost`) gained a `pickFilePath(...)` method whose **default returns `false`** (so the modules stay standalone + portable for POM2 and keep their built-in ImGui browser as the WASM/no-zenity fallback); POM1's hosts override it to call `NativeFileDialog::pickFiltered` (a CSV-extension convenience over `openFile`/`saveFile` that appends an "All files" filter on loads). The paint/bench hosts get the GLFW parent via a `GLFWwindow* const*` slot pointing at `MainWindow::window` (dereferenced lazily at pick time because the hosts are constructed before `ctx.window` is set); `Pom1BenchHost` reads `mw_->window` directly as a friend. Each editor's `openFileBrowser`/`browse` tries `pickFilePath` first and only opens its ImGui popup when that returns false; the action dispatch is factored into `performFileAction` so both paths share it.
- **`MachinePresets.{h,cpp}` — the preset table, UI-free.** `kMachinePresets[]` is pure data (cards, RAM, BASIC, first-run window placements) that the CLI, the DevBench target table and the Hardware → Preset menu all read, so it must not be reachable only through the UI. It used to live in `MainWindow_Presets.cpp`, which forced `CliDispatcher.cpp` to `#include "MainWindow_ImGui.h"` for **two static accessors** — dragging ImGui + GLFW into anything that linked the CLI parser, and that is exactly why `parseCli()` was the one July-2026 test hole left unfilled. It is now its own TU in namespace `pom1`, consumed via `pom1::machinePresetCount()` / `machinePresetName()`; `MainWindow_ImGui::getPresetCount/Name` are forwarders. **The TU must stay UI-free**: it may include peripheral headers but never `imgui.h`, `GLFW/glfw3.h` or any `MainWindow_*` header, which is why `MachineWindowPlacement` carries a POD `PresetVec2` instead of `ImVec2` (the UI converts at `detail::toImVec2`). `MainWindow_Internal.h` re-exports the names with using-declarations — **not cosmetic**: the MainWindow methods sit in the global namespace and reach `detail` through a using-*directive*, which never runs enclosing-namespace lookup. Pinned by **`cli_dispatcher_smoke`**, whose real assertion is that it LINKS: re-couple the dispatcher to the UI and that target stops building. Note `preset_ram_profiles_smoke` parses the table as TEXT, so its `add_test` argument points at `MachinePresets.cpp` — move the table and you must move that path too.
- **The UI holds no copy of the machine's topology.** Sixteen `bool xEnabled` members used to mirror what was plugged, written at every toggle, every preset apply, every CLI override and every cascade ("mirror UI", "sync UI", "mutual exclusion" — the comments name themselves). A second copy is a thing that can disagree, and that family is where the BBS auto-dial regression came from. They are gone; three members replace them: **`currentCards()`** — the staged target while a card transaction is open, the machine's published `CardSet` otherwise (`pom1::StagedCardConfiguration::effectiveCards`, pure and pinned by §7 of `staged_card_configuration_smoke`) — plus **`cardPlugged(CardId)`** to ask and **`setCardPlugged(CardId, bool)`** to tell. The staged half is what the mirrors were really for: a checkbox has to tick the moment it is clicked, and a staged plug does not reach the machine until the transaction commits. `setCardPlugged` issues the command **and re-reads the snapshot**, so the rest of the frame sees the cascades it triggered (Parmigiani evictions, daughterboards) instead of the pre-command copy — one snapshot copy per user click, against a rule that already lives in `CardTopology`. `plugGen2()` is the same for the GEN2 card, which attaches through its framebuffer rather than the generic card path. `EmulationSnapshot::cards` publishes the topology as one value; the per-card bools that remain are the hooks the peripheral sub-snapshots hang off, not UI state. Consequences worth knowing: `wouldCreateConflict` / `listParmigianiConflicts` / `resolveParmigianiConflicts` stopped hand-rebuilding a `CardSet` from ten mirrors (three copies of the same ten lines), the window registry's `gate` names a `CardId` instead of a `bool MainWindow_ImGui::*`, and `gateStrictPlug` takes its flag **by value** — there is no mirror left to revert, so refusing is the whole answer.
- **Testable logic extracted out of MainWindow** (`Apple1KeyMap`, `FullscreenExpand`, `WindowGeometry` — pinned by `mainwindow_logic_smoke`). The UI is deliberately kept out of every test binary, which left POM1's largest layer uncovered — and it is exactly where the august 2026 bugs lived (the destructive backspace, six defects in the fullscreen path); neither could be pinned where it stood. These three carry **no ImGui and no GLFW**, so they link on their own without `POM1_TEST_CORE_SOURCES`: `Apple1KeyMap::mapKey(key, mods)` is the whole host-key → Apple-1-byte decision, `FullscreenExpandSettler` the settle-on-DisplaySize rule, `WindowGeometry` the `.size` sidecar format plus the off-screen rescue. **`LayoutDecisions.h` is the fourth, and it closes the fullscreen path**: the timing and the format were out, the ARBITRATION was not. Header-only (so `sources_outside_test_devices` did not move), pinned by `layout_decisions_smoke` — `decidePersistedGeometry` (the windowed rect is ALWAYS what `ini/preset_NN.size` carries; `GLFW_MAXIMIZED` is meaningless inside a macOS space, where AppKit reports the underlying window's zoomed state; a kiosk `--fullscreen` must not rewrite the profile as fullscreen, yet cannot suppress mode 2), `planLayoutRestore` (five branches — fullscreen is a SESSION property, never a per-profile one, and a native space is never re-entered programmatically), `planLayoutReset` (including dropping the `Apple 1 Screen` placement, without which the `ImGuiCond_Always` force stamps the windowed rect back over the expand), `placementApply`, the checkbox pair `fullscreenCheckboxState`/`planFullscreenToggle` (AppKit keeps the style mask set for the whole ~0.5 s exit animation, so the raw answer re-ticks the box and invites the second click that puts the window straight back in), and `computeOsWindowSize` — ONE function for the three copies of that arithmetic (desktop, WASM canvas, `.size` pre-generation), carrying the POM1 Fantasy floor and its deliberate absence in the browser. **`PresetDecisions.h` is the fifth**: what applying a preset MEANS, once. `MachinePresets.h` owned the data and `CardTopology.h` the card policy; the composition stayed in `applyMachineConfig`, where three rules were each stated TWICE under a "keep them in sync" comment — the twelve-flag silicon-fidelity bundle (preset path + the Silicon Strict master button, now both going through `siliconFidelity()` and the single applier `MainWindow_ImGui::applySiliconFidelity`), the `applesoftOnSdCard()` predicate (which decides BOTH the ROM profile the controller loads and the inventory the Memory Map shows — and had a THIRD copy on the headless path, so a headless boot could load a different BASIC than the profile the user sees), and "is this a DevBench profile?" (an index range in one place, three `PresetId` comparisons in the other). Plus `tapeFor` (which preset preloads which tape, and which of them is cassette DATA rather than deck music), `animatesBoot`, `showsBanner` and `coldResetOnApply`. Pinned against the REAL thirteen-preset table by `preset_decisions_smoke`. **Window presence is the registry's job now**: the 47-line `showXxx = false;` recitation and the 36-branch `else if (n == "<title>")` auto-show chain are two loops over `windowRegistry()`, which gained a `resetOnPresetSwitch` column (default TRUE — a window belongs to a preset unless the user works IN it: Bench, editors, inspectors, Memory Viewer, Debugger). That set HAD diverged: the IEC tutorial was missing from the close list, alone among sixteen tutorials in surviving every profile switch. **`ShortcutTable.h` is the sixth**: the eight host-side key bindings as `constexpr` data. The table called itself the single source of truth for the menu labels AND the dispatcher, and was — for three of its eight rows; the other five carried a null action dispatched by an `else if (key == GLFW_KEY_F1) …` ladder underneath, and Help ▸ Keyboard Shortcuts held a THIRD copy as hand-written prose under a "update both together" comment, which made the list the user reads to learn the keys the copy most likely to be stale. A row now names a `Command`, the dispatcher is one switch over it, the Help window renders the rows it dispatches, and autorepeat is a per-row property (only hold-to-step wants it — a repeating hard reset is a boot that never finishes). **The `no CTRL+letter` invariant is now a `static_assert`** on the real table in `MainWindow_Keyboard.cpp`, so adding such a row fails the build; `shortcuts_sync` is kept and repointed because it reads the SOURCE TEXT and so still catches forms the C++ predicate would accept (a key spelled as a raw number), and it names the shadowed control code. Pinned by `shortcut_table_smoke`. **`TerminalTiming.h`** is the ninth (after `CommandPalette.h`): how long PB7 ($D012) stays busy after a display write — the most-executed timing in the machine, since every printing program spins on the Woz Monitor's `BIT $D012 / BMI`. Two models: the historical `FixedDelay` countdown of `CPU_HZ/60` = 17045 cycles (the default, and what every shipped program and golden image is validated on) and `FieldSync`, busy until the next 60 Hz field boundary — 65 × 262 = **17030** cycles, the raster period resolved with Uncle Bernie in `doc/GEN2_RELEASE.md` Q4, which POM1's derived 1/60 s misses by 15. FieldSync models a terminal that has no framebuffer: the text recirculates through a shift register scanned at the video rate, so a character can only be latched when the scan reaches the cursor. **Throughput is identical either way** — consecutive writes stay exactly one field apart whatever the phase, so the documented 60 characters/second holds (`terminal_timing_smoke` §3); only where the wait falls moves. It is OFF everywhere by default and **no preset arms it**, because the phase-locked model is *reasoned from the schematic, not measured on a terminal section* — the header says so and names what would confirm it. `--display-field-sync` and the Silicon Strict inspector toggle it. **`SoftwareDirRules.h` is the seventh**: which card a shipped `software/` directory implies, in BOTH directions. Loading from `software/Graphic HGR/` plugs GEN2 and opens its framebuffer; from `software/NET/` it plugs the Wi-Fi modem, or RESETS it when a BBS session is already up. That was a seven-branch `else if` chain of `path.find("/X/") || path.find("\\X\\")` in `performMemoryLoad`, while the file picker held the same relation backwards (`memoryContextSubdir`) under a comment saying so. Three things the one table makes testable: the match is on a path COMPONENT under either separator **and a mix of them** (a bare substring fires on `software/NETWORKING/`; a missing backslash form is dead on Windows and nowhere else), FIRST rule wins on a path carrying two markers (the `else if` order, now a property), and `isPickerDefault` is a field rather than a comment — microSD plugs on load but must never be the folder the picker opens into, its content living on the SD filesystem. Consequences stay on the rule that wants them: `evictStorageCards` for the two graphics cards only (Fantasy plugs microSD/CFFA1, whose $6000-$AFFF windows shadow the program and show as a BLACK CARD, not an error) and `resetWhenAlreadyPlugged` for the modem only — though *what* a reset is stays in the UI, so a future rule raising the flag cannot silently drop a BBS session. Pinned by `software_dir_rules_smoke`. MainWindow keeps only what genuinely needs the live UI — focus guards, autorepeat gating, file paths, GLFW monitor enumeration, and the GLFW/AppKit calls each plan above describes. **`Apple1KeyMap` mirrors GLFW's key/mod values rather than including the header**; `MainWindow_Keyboard.cpp` `static_assert`s the mirror against the real macros, so the duplication fails to compile rather than silently rotting. Grow this seam when adding UI logic: anything that is a decision rather than a draw call belongs on this side of it.
- **MainWindow_ImGui** — single class across 14 TUs (`MainWindow_ImGui.cpp` + `_Dock`, above, plus the 12 below), all but `_Keyboard` sharing `MainWindow_Internal.h`: `_Layout`, `_Presets`, `_Menu`, `_Dialogs`, `_Settings`, `_Tutorials`, `_HardwareWindows`, `_SiliconStrict`, `_FileDialogs` (auto-enable-by-directory), `_DebugWindows`, `_Keyboard`, `_TMS9918Inspector`. The last four splits are the août-2026 god-file pass and are **pure code motion** (`_Settings` + `_Tutorials` out of a 3559-line `_Dialogs`; `_SiliconStrict` — Parmigiani's conflict table + `gateStrictPlug`/`wouldCreateConflict` + the inspector — out of `_HardwareWindows`, because that policy is not a rendering detail and the open "data-drive the 52 `Begin` blocks" item needs it somewhere of its own). **`kMachinePresets[]` no longer lives in `_Presets`** — see `MachinePresets.h` below. Keyboard bypasses `InputQueueCharacters` — keys go GLFW → Apple 1 directly. With autorepeat off (default, matches TTL keyboards) REPEAT drops printable+Enter/Backspace/Escape; F7 hold-to-step honours REPEAT. **CTRL+letter → `$01-$1A`** is queued from `handleGlfwKey`, not the char callback: GLFW emits no char event for a CTRL chord, so without it no control code was reachable from the physical keyboard (Ctrl-C = Integer BASIC break, Ctrl-H = Applesoft Lite's line editor) — only from the keyboard-photo overlay's sticky CTRL latch, whose `toupper & 0x1F` fold it mirrors. ALT/SUPER excluded (Cmd- stays with the OS), SHIFT allowed. **The binding table must never hold a CTRL+letter chord** (`pom1::shortcuts::kBindings` in `src/ShortcutTable.h`; enforced since 24 août 2026 by `tools/check_shortcuts.py`, ctest **`shortcuts_sync`**, and since septembre 2026 by a `static_assert` in `MainWindow_Keyboard.cpp`) — it dispatches before the Apple-1 sees the key, so such an entry silently makes that control code untypeable; `Ctrl+O/S/V/Q` (Load/Save/Paste/Quit) were removed for eating `$0F`/`$13` XOFF/`$16`/`$11` XON and live in the File menu only. Function-key chords are safe (not ASCII), so `Ctrl+F5` = hard reset stays. **Host Backspace sends `_` (`$5F`), never `$08`** — the Apple-1 has no hardware that can delete the character left of the cursor, and the Woz Monitor's GETLINE ECHOes every key *before* `CMP #$DF`, so the `_` is already on screen when BACKSPACE fires and all it does is `DEY`: the char leaves the input buffer, the screen keeps the underscore trail (github #38). `$08` would print nothing and leave a junk byte, NOTCR testing only `$DF`/`$9B`. Applesoft Lite's Ctrl-H editor is reached as a CTRL+letter chord instead. The physical DEL key is deliberately unmapped; the keyboard-photo's RUB OUT still sends `$7F`, which the Signetics fold displays as `_` anyway.
- **Screen_ImGui** — 40×24 grid; 2 charmap modes (Apple1/HostAscii), 3 monitor tints (Green/Amber/Mono). **Charmap text renders to ONE native-resolution framebuffer** (`buildScreenFramebuffer`: 40×24 cells × 7×8 Apple-1 dots → `kFbWidth`×`kFbHeight` = 280×192, the 5×8 charmap glyph inset by `kGlyphXOffset`), uploaded as a `Filter::Nearest` texture (like the GEN2/TMS9918/GT-6144 cards) and drawn with a single `AddImage` scaled to the display rect — the rect's aspect applies the `kApple1RasterWidthScale` non-square-dot squish. White dots tinted by the `AddImage(col)` param, so mode/brightness changes need no rebuild; the FB is re-rasterised only when the effective grid (content + cursor + power-on pattern) changes (`screenFbContentValid` / `lastEffectiveGrid`). **This replaced the old per-glyph scaled-atlas blit**, whose double-resample garbled characters under the Metal nearest-sampler patch (a 32×40 cell baked for linear, point-sampled to a non-integer size). HostAscii / no-renderer keep the per-cell fallback (`drawCharmapGlyph` / `AddText`). CRT scanlines = 1-px `AddRectFilled` every 2 display pixels at integer Y. `AddLine` avoided — its AA on macOS GL 3.2 / WebGL2 splits sub-2-px thickness across two rows and halves alpha.
- **CRT effect stack** (`CrtEffectStack` + `CrtParams` + `OpenGLShader` + manager `Pom1CrtEffects`, ported from POM2) — universal GPU post-process, **ON by default** (opt-out via the master button in Settings → "CRT Effects (sliders)..."; a saved `crt_enabled=0` is respected), applied to **every** emulated framebuffer: text screen + GEN2/TMS9918/GT-6144 windows. One shared `CrtParams` (MainWindow-owned, persisted `ini/ui.settings` `crt_*` keys) drives a **per-slot** effect stack (`Pom1CrtEffects::Slot`, one ping-pong pair per framebuffer for phosphor persistence). Single call site `crtEffects.apply(slot, tex, srcW, srcH, dstW, dstH)` → returns the ImTextureID to draw (processed output, or the raw texture on OFF / failure / headless). **Two backends, one look**: `CrtEffectStack` (GL/GLES — reaches the raw GLuint via `PomRenderer::glTextureName()`/`isOpenGL()`, FBO ping-pong) and `CrtEffectStackMetal` (macOS — `metalTexture()`/`metalDevice()`/`metalCommandQueue()`/`isMetal()`, MTLRenderPipelineState + two private RGBA8 render targets). `Pom1CrtEffects::ensureInit()` picks one from the live renderer; the other array stays empty. Each file stubs out on the backend that isn't its own, so both always link. **The two shaders are hand-kept in lockstep** — GLSL 150/300-es in `CrtEffectStack.cpp`, MSL in `CrtEffectStackMetal.mm`, same effect order and constants; a knob added to one must be added to the other or macOS silently diverges. MSL gotchas already handled: `fmod` truncates toward zero where GLSL `mod` floors (barrel warp pushes uv negative at the corners → mask misphase), and Metal render targets are **top-left** origin so the vertex stage emits `uv.y = (1 - pos.y) * 0.5`. The Metal pass encodes on its **own** command buffer committed during the UI build — the ImGui frame's buffer is created in `beginFrame()` but only enqueued at `present()`, and Metal orders by enqueue, so the effect always lands before the draws that sample it. The pass renders at **on-screen resolution** (scanline/mask patterns analytically anti-aliased via `fwidth`, no downstream resample); when `active()`, the legacy ImGui scanline/phosphor overlays are skipped (`Screen_ImGui` + GEN2 window) to avoid double-dipping — monitor tint still applies via the `AddImage(col)` param.
- **Bench** (`Pom1BenchHost.cpp` + `Pom1BenchHost_Lang.cpp` + `Pom1BenchTargets.{h,cpp}` + `Pom1BenchCc65.{h,cpp}` here, portable `bench/CodeBench.cpp` + `BenchLang.cpp` + `IBenchHost.h` under `src/bench/`). The host was a 3957-line god file; août 2026 split it on real seams, all **pure code motion**: **`Pom1BenchTargets`** owns the `kP1Targets[]` (language × machine) table + the hello-world starter sketches + the two path helpers (`benchScratchDir`, `codeTankBasicLogoRomReadPath`) — data, exactly like `MachinePresets`; **`Pom1BenchCc65`** owns the pure string/path layer (Makefile + linker-cfg probing → `AsmProjectCtx`, the JSON C build spec, the `ar65` runtime-archive cache, the cl65/ld65 command builders) with no MainWindow / EmulationController / ImGui in sight — keep it that way; **`_Lang.cpp`** owns interpreter INJECTION (`injectBasic`, `injectLogo`). The split line there is *injection vs toolchain*, not "language stuff": `compileBasicNative` is a BASIC path too but it shells out to ca65/ld65 and shares the cc65 plumbing with `build()`, so it stayed beside that pipeline. **Source-level debugging (asm targets, desktop)**: the asm path assembles `-g` and links `--dbgfile`; `src/DbgFile.cpp` (pure, `dbgfile_smoke` + `bench_cc65_smoke` — the latter also the first test on `Pom1BenchCc65.cpp`) parses it into addr↔line tables — **code only**: spans carrying `type=` are data (`.byte`…) and line records with `type=2` are macro BODIES, both excluded so a breakpoint can only land where the PC actually goes (`.res` is the known blind spot). **`bench_debug_protocol_smoke` runs the host's own sequence (line→addr→arm→run→halt→resume) against a real M6502**, which is as close to `Pom1BenchHost` as a test can get — it needs a live MainWindow, so everything above it is verified by reading only. Two non-obvious CPU facts that shape the code and are pinned there: `M6502::run` tests the breakpoint at the TOP of its loop (so resuming while parked on the armed address re-trips without executing — resume must step first), and `setBreakpoint()` CLEARS the trip latch (so "should I step first?" must be asked as *stopped AND PC == armed address*, never via `isBreakpointTripped()`). Every machine reset (`loadBinary`, `hardReset`) disarms the CPU breakpoint, so each Run path re-adopts the fresh table and re-arms AFTER its last reset; the host feeds four neutral-default `IBenchHost` virtuals (`debugLineInfo`/`sourceLineForPc`/`toggleLineBreakpoint`/`breakpointLine` — one breakpoint, the machine's single CPU breakpoint) and pours the program's labels into the disassembler's `SymbolTable`. **The decisions live in the pure `BenchDebugSession` (`bench_debug_session_smoke`), not in the host** — same seam rule as `Apple1KeyMap`/`WindowGeometry`: it does NOT own the machine's breakpoint (every query takes the live `(armed, address)` and every answer is an intention the host carries out), which is what makes "is this breakpoint still ours?" answerable without an emulator, and it is why a `Cleared` toggle is distinguishable from a `NoCode` one; CodeBench decorates ONLY the tab the last build described (`dbgDocUid_`) and drops everything on a dirty buffer. Details → [`doc/DEVBENCH.md`](DEVBENCH.md), WASM specifics → [`doc/CC65_WASM.md`](CC65_WASM.md). Desktop uses bundled cc65 (`ca65/ld65/cl65`) resolved exe-relative first (`<exe>/cc65/bin`, macOS `<exe>/../Resources/cc65/bin`, AppImage `<exe>/../share/POM1/cc65/bin`) so packaged builds are self-contained. **WASM ships the full cc65-in-WASM toolchain, so it exposes every target (asm/C/hex/BASIC) — same matrix as desktop, identity `targetMap_`.** The one exception is the two **native** Applesoft targets (12-13): still listed, but the mode-5 dispatch refuses them in the browser and `nativeSiblingOf()` returns -1, so the Inject/Native toggle collapses to Inject. **C targets link the runtime as an `ar65` ARCHIVE** (per-module `.o` → `rt.lib`, mtime-cached under `benchScratchDir()/rtlib_<target>` on desktop, same model in-browser) so ld65 dead-strips unused families — direct objects always link whole, which is why the old single-`cl65` command force-linked the whole ~20 KB gen2c runtime (kept only as the no-`ar65` fallback). Spec field `userAsm` (a sketch's `EXTRA_ASM`) = direct objects, never archived — they must survive unreferenced. See DEVBENCH.md "Link model".

  - **macOS ships ONE Universal 2 (arm64 + x86_64) `.dmg`, and NEVER links a Homebrew dylib.** Both are the same lesson: `brew` installs exactly one arch and the linker bakes brew's *absolute* prefix into the binary, so the old `brew install glfw` job produced an x86_64-only app hard-wired to `/usr/local/opt/glfw/lib/libglfw.3.dylib` — a path that doesn't exist on Apple Silicon (brew is `/opt/homebrew` there), so every shipped DMG died at dyld and Finder blamed it on the misleading "POM1 quit unexpectedly". The CI smoke-launch structurally *cannot* catch this: the runner has brew glfw at that exact path. `packaging/macos/build_universal_deps.sh` builds both deps from source for both slices — **GLFW statically** (no dylib left to resolve at all) and **cc65 universal** (it ships inside the `.app` and the DevBench *executes* it, so a single-arch toolchain would mean Rosetta-or-nothing). `package_macos_release.sh` honours `POM1_MACOS_ARCHS` (unset ⇒ native-only, what a dev wants) + `POM1_BUILD_DIR`, bundles any surviving non-system dylib into `Contents/Frameworks` with `@rpath` install names, and hard-fails on a leftover `/usr/local`, `/opt/homebrew` or `/opt/local` reference or a missing slice — including on the five cc65 tools. The release job runs on `macos-15` (arm64) and cross-compiles the x86_64 slice; that slice is verified by `lipo`, not run, since GitHub's arm64 images ship without Rosetta.
- **HGR Paint editor** (`src/Pom1HgrPaintHost.{h,cpp}` here, portable `src/hgrpaint/` — `HgrPaintEditor`, `HgrPaintModel`, `IHgrPaintHost`, plus the image importer `Cam16` + `HgrConvert` + `HgrImageDecode` — same split as Bench, intended for POM2 reuse). The editor + model depend only on ImGui/GL/`IconsFontAwesome6` and the `hgrpaint::IHgrPaintHost` seam (poke / `renderHgrPage` / file I/O); POM1's host wraps `GraphicsCard` + `EmulationController`. The pure model owns its own Apple II HGR interleave + geometry constants (no `GraphicsCard` dependency). **Flood fill floods by *perceived* artifact colour** (renders the page through the host NTSC pipeline): a chromatic field is bit-dithered (solid violet = `$55`, odd columns off), so a raw-bit flood leaks through it — `fillRegion` clears the region then stamps the new colour's parity pattern. **Image import (PNG/JPG → HGR)** is ii-pix-style analysis-by-synthesis: `HgrConvert` carries its *own* copy of the MAME NTSC decode (byte-identical to `GraphicsCard`, pinned in `hgr_convert_smoke`), scores candidate byte patterns in CAM16-UCS (`Cam16.cpp`, chroma-weighted) and Floyd-Steinberg-dithers. - **The sprite catalogues are a data format with THREE parties, and two of them fail differently** (`sprite_catalogues_smoke`). `dev/lib/tms9918/sprites_*.asm` are hand-written masters; `tools/build_hgr_sprites.py` GENERATES `dev/lib/gen2/sprites/sprites_*_hgr.asm` from them; ca65 `.include`s either, and the emulator parses both into the two sprite editors' Dev library. **ca65 stops on a malformed file and says so; `parseSpritesAsm` drops what it cannot read** — a sprite lost to a mistyped `.byte` row is a catalogue silently one entry short. `sprite_asm_export_smoke` pins the GRAMMAR (round-trip + a hand-written fixture); `sprite_catalogues_smoke` pins the 32 SHIPPED FILES against it: the count each header declares about itself, the family's geometry (48 B HGR / 32 B TMS), no empty or duplicate names, and the generator's contract — each HGR catalogue must still name the same sprites in the same order as its TMS master, which is how "edited a master, forgot to regenerate" is caught without running the generator. **Consecutive labels are ALIASES**: the masters emit `chess_king_pat:` and the cc65-callable `_chess_king_pat:` back to back, and the parser used to consume the slot comment on the first, so the same sprite read as `rat` in the HGR editor and `_fauna_rat` in the TMS one. The discriminator is the exact cc65 convention (same label, leading underscore, no bytes between) — "the previous label had no bytes" is too loose, since every catalogue opens with a base label that has none either.
- **HGR Sprite editor** (`src/hgrsprite/` — `HgrSpriteEditor` + the pure `HgrSpriteBlit`; **reuses the `hgrpaint::IHgrPaintHost` seam + `HgrPaintModel` verbatim**, so `Pom1HgrPaintHost` doubles as its host — MainWindow constructs it with `hgrPaintHost.get()`). - **TMS9918 Paint editor** (`src/Pom1TmsPaintHost.{h,cpp}` here, portable `src/tmspaint/` — `TmsPaintEditor`, `TmsPaintModel`, `ITmsPaintHost`, plus the importer `TmsConvert` + `TmsImageDecode`; reuses `hgrpaint/Cam16` + `HgrFont` verbatim). Same split + seam shape as the HGR editor, but for the P-LAB Graphic Card. **Two canvas modes**, each with a FIXED canonical VRAM layout the editor programs onto the live chip (registers + name table) so what's poked actually displays: **Graphics II** (256×192, name `$1800` identity, pattern `$0000`, colour `$2000`) and **Multicolor** (64×48 blocks of 4×4 px, per-section name table `name[r*32+c]=(r/4)*32+c` so every block addresses a distinct nibble). The rendered texture is always the chip's 256×192 active area — in Multicolor a logical block spans 4×4 texture px (`lpx` factor threads through all mouse/overlay math). The **central constraint is Graphics II colour-clash**: each 8×1 cell holds only 2 colours (`fg`/`bg`); `plotPixel` reassigns whichever slot disturbs fewer of the cell's other pixels, and `TmsConvert` picks the best 2 of 15 palette colours per cell + Floyd-Steinberg-dithers (CAM16-UCS, no NTSC synthesis — the palette is 15 fixed RGB). The seam uses **VRAM addresses** (0..`$3FFF`), not CPU addresses (TMS9918 VRAM is behind `$CC00/$CC01`); the host forwards pokes/register writes through `EmulationController` to `TMS9918::editorPokeVram`/`editorSetRegister` (out-of-band edits that bypass the silicon-strict drain — never counted as dropped writes). **The canvas displays the chip's OWN live framebuffer** (`TMS9918::copyActiveFramebuffer`, the active 256×192 of the 288×216 raster — exactly what the Graphic Card window shows) rather than re-deriving the image from VRAM, so it never diverges from the real card; `renderToBuffer` is used only for the import preview (a hypothetical VRAM not yet on the chip). Entering the editor is **non-destructive** — the canonical paint registers + name table are pushed to the chip lazily on the first edit (`ensureModeApplied`, via `beginStroke`) or an explicit mode pick, so merely viewing the card doesn't disturb a running program. Pinned by `tms_paint_plot_smoke` + `tms_convert_smoke` (both cross-check the model's VRAM addressing + the converter against the real `TMS9918` per-line renderers — install canonical tables, plot/convert, render, assert the displayed colour).
