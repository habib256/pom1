# POM1 loaders, containers and host services

The file formats POM1 parses (memory images, cassette containers, hex dialects),
the audio and logging seams, and the host-side rules each one is bound by.

Split out of [`CLAUDE.md`](../CLAUDE.md), which keeps the short version and
points here. Doc map → [`doc/README.md`](README.md).

---

- **WAV and AIFF are parsed by POM1, not miniaudio — and the parsers live in `src/PcmFile.{h,cpp}`, pure.** `ma_decoder` covers MP3/FLAC (+Vorbis) and has no AIFF backend, but AIFF is what Uncle Bernie's `ACIace` tape synthesiser emits, so POM1 reads big-endian IFF by hand (COMM/SSND, the 80-bit extended sample rate, PCM 8/16/24/32 + AIFF-C `sowt`/`fl32`); the RIFF/WAVE reader is its little-endian twin. `parseWavPcm` / `parseAiffPcm` take **bytes and return mono float + rate + error/warning** — no device, no file, no log sink — and `CassetteDevice::loadPcmTape()` is the shared size-check-read-parse-decode body behind both `loadWavTape` and `loadAiffTape`. Traps they handle: AIFF PCM is **signed at every width** including 8-bit (WAV's 8-bit is unsigned — confusing them is a full half-scale DC offset the pulse decoder reads as one unbroken level); chunk sizes are compared against the bytes **remaining**, never `offset+size`, which wraps on wasm32; SSND's alignment offset must stay inside its chunk; COMM's frame count wins only when it is the **smaller** of the two; and `.aiff` takes the **pulse path unconditionally** like `.aci` — it is cassette DATA, never deck music, and audio-stream mode would carry no transitions for `$C081` to read. **Hardening:** `kMaxPcmFileBytes` (256 MB, checked before the file is read) and `kMaxPcmFrames` — the latter is not new, it is the thirty-minute cap `loadMiniaudioTape()` has always applied, whose comment says it "prevents accidental 2-hour podcast loads from chewing memory"; the two hand-rolled parsers had **no cap at all**, so exactly that case was refused as an `.mp3` and accepted as a `.wav`. `kMinPcmSampleRate`/`kMaxPcmSampleRate` bound a field the WAV parser did not bound at all, and whose low end made the downstream `deltaSamples × CPU_HZ ÷ rate` narrowing **undefined behaviour** (`pcmToDurations` now clamps in the double domain before narrowing, because miniaudio-decoded files reach it too). Non-finite samples in a float container become silence with a warning — every comparison against a NaN is false, so a corrupt float WAV used to read as a flat line and be reported as "no detectable cassette signal".
- **Audio is a service the core is HANDED, never one it builds — `pom1::IAudioService` (`src/AudioService.h`).** `Memory` used to `make_unique<AudioDevice>` in its constructor, so every core reached for the host's sound hardware on the way up, a test core included. `main_imgui.cpp` now owns the `AudioDevice` (GUI **and** headless) and passes it down through `MainWindow_ImGui` → `EmulationController` → `Memory`, which keeps a plain pointer and owns one only when nothing is injected. Three consequences, and each is the point of a different half of the change: **(1)** `--audio-latency` is a constructor argument instead of `AudioDevice::setPreferredLatencyMs`, a static whose only reason to exist was reaching across the gap between `main()` and a device built four layers down. **(2)** `Memory`'s `initializeAudioHardware` now defaults to **false**, because `Memory mem;` appears in 50 test files and every one of them opened a real OS sound device (~21 ms each, ~100 ms for the first in a process, plus miniaudio errors on a soundless CI box) to run tests that never listen. `EmulationController`'s flag follows for the same reason. **Measured by counting miniaudio's own open line across a full `ctest`: 161 → 0.** The frontends pass `true` explicitly, so nothing audible changed — `--audio-latency 120` still logs `output cushion 120 ms (1764 frames x 3 periods)`. **(3)** `~Memory` unregisters its sources (`removeSource` is a lifetime barrier): an injected service outlives the machine, so the member-declaration-order rule below is no longer the only thing between the mixer and a dangling `CassetteDevice`. `pom1::NullAudioService` is the in-memory double — no mixer, no scratch, no threads — and is **not** `AudioDevice(false)`, which still mixes and is what the audio tests use. Pinned by `hermetic_core_smoke` §4.
- **`AudioDevice::getActualSampleRate()` returns the miniaudio-negotiated rate** (44.1 kHz requested, often 48 kHz on Apple Silicon) — cycle-driven sources must use this or tempo drifts. WASM always 44.1 kHz.
- **The audio callback must not allocate and must not wait on slow work.** `AudioDevice::mixSources` runs on the OS audio thread. Its scratch (`tmpBuf`) is sized ONCE in the constructor (`kMixScratchFrames`, 8192) and a larger request is mixed in chunks rather than growing the buffer — a heap allocation there can take an allocator lock and blow the buffer deadline. The same rule governs every `AudioSource::fillAudioBuffer`: **SID is the reference** (lock-free SPSC ring, `chipMutex` deliberately NOT taken, said so in its header), and `CassetteDevice` now follows it — `loadAudioStream` builds the `ma_decoder` OUTSIDE `audioStreamMutex` and swaps a `std::unique_ptr` under a short lock, `closeAudioStream` steals the pointer under the lock and runs `ma_decoder_uninit` outside it. It used to hold that mutex across `ma_decoder_init_file()` plus a frame count that can walk a whole MP3, so inserting a tape dropped audio for as long as the media was slow. **The decoder must stay heap-owned**: miniaudio's data-source base holds pointers into the object, so a by-value `ma_decoder` cannot be moved in after init. Note what can and cannot catch this class of bug — it is neither a lock-order inversion (`src/LockOrder.h` is blind to it) nor a data race (TSan is blind to it); it is purely how long a lock is held, so no CI job substitutes for reading the call path.
- **`~CassetteDevice()` is not `= default`** — a mounted stream tape owns a live `ma_decoder`, and only `ma_decoder_uninit` releases the backend's buffers and file handle. Destroying the owning pointer alone leaks them, which the nightly ASan job (`detect_leaks=1`) would report.
- **`logs/pom1.log` is the only log sink that outlives the process.** `src/Logger.h`'s `StreamLogger` writes to stdout — which goes nowhere on a Finder/Explorer double-click — and `RingBufferLogger` dies with the process, so before `FileLogger` a user had nothing to attach to a bug report, crash or not. It is the third child of the `TeeLogger` installed by `initDefaultTeeLogger()`: timestamped to the millisecond, flushed per entry (the entries that matter most are the last ones before a hang), rotated one deep at open, and a silent no-op when the file cannot be opened. **`pom1_macos_provision_user_data_dir()` must run BEFORE `initDefaultTeeLogger()`** — it is what `chdir`s into `~/Library/Application Support/POM1/`, and the sink resolves its relative path against the working directory; installed the other way round, a Finder launch wrote its log wherever Finder started us. Not installed under WASM (virtual FS, discarded on reload).
- **OOR (`ramKB < 64`)**: strict mode returns `$FF` and drops writes in `[ramKB*1024, $8000)` — matches real Apple-1 with no RAM board. Status bar: `OOR:N!` or `[strict]`.
- **`loadHexDump` has THREE parsers, picked by content — and they live in `src/MemoryImageLoader.{h,cpp}`, not in `Memory`.** `pom1::parseMemoryImage(content, fileName)` is **pure**: bytes and a name in (the name is never opened — it supplies the display string and the one `.tur` extension rule), a `MemoryImage` out carrying the writes as contiguous spans, the run address, a byte count and severity-tagged diagnostics. It touches no `mem[]`, no filesystem, no log sink, so `Memory::loadHexDump` is now *parse → decide → apply* and `memory_image_loader_smoke` reaches every dialect without an emulated machine. **Nothing partial ever escapes**: a rejected image drops every span, which the in-place loader could not promise — it wrote each Intel HEX record into RAM as it recognised it and only then discovered the record past `$FFFF`, and a file that established no address at all dumped its stray bytes into page zero before returning the error. Spans **are** the Memory Map zones (both are maximal contiguous runs). Default parser (legacy): joins every line into one string and recovers boundaries heuristically — comments (`//` `#` `;`, stripped inline, else `LDA`/`DEX` mnemonics parse as data), continuation lines, `R` suffix (run address), and **merged data+address** (`ED0300:` → data `ED` + addr `0300`, the artefact of that joining). A **TurboType `.TUR`** takes a **line-structured** parse, and an **Intel HEX** file takes `src/IntelHexFile.h`. Applying the result deliberately **bypasses the ROM write-protect** — a WOZMON dump is the user typing at the Monitor. **Hardening:** `kMaxMemoryImageBytes` = 8 MB (largest shipped dump ~100 KB; a full 64 KB image in WOZMON runs a few hundred KB) — `Memory::loadHexDump` checks the file's **size before reading it**, `parseMemoryImage` re-checks for every other caller, and both share `memoryImageTooLargeMessage()` so the two refusals cannot drift. Address tokens go through a **checked accumulator, never `strtol`**: `long` is 64-bit on macOS/Linux and 32-bit on Windows, so an over-wide token saturated differently on each — a TurboType line reading `100000000` truncated to `$0000` on the 64-bit hosts, putting the bytes that followed into **page zero**, while the 32-bit host clamped elsewhere and dropped them. The line-structured parser has no merged-token rule to fall back on, so it now skips and reports such a line; the joined parser keeps its documented merged data+address reading of the same token. Odd-length runs report the **address** of the first one, not just a count.
- **Why `.TUR` needs its own parser:** a turbo block puts the address on its own line and prefixes each 16-byte data line with `:` — the inverse of WOZMON's `AAAA:` suffix. Joined, every 32-digit data run is followed by the next line's `:`, so the legacy "hex token before `:` is an address" rule sliced off its last 4 digits as an address and **shredded the 15 Puzzle's $0300 block into 60+ bogus zones** ($18A9, $4159, $F460…). Keeping lines apart makes both dialects unambiguous and needs no merge hacks. `X` is a bare end-of-stream marker (it used to also swallow the `015ER` run line behind it, so POM1 jumped into the serial receiver at `$0100` instead). **Selected by the `.tur` EXTENSION *or* a lone `T` line** — the marker is optional in the wild (the same transfer is also published as plain address + `:data` blocks), and a marker-less file left to the legacy parser hits exactly the shredding above. Everything else still needs its `T`, so the ~100 bundled `.txt` dumps keep byte-identical legacy behaviour.
- **Intel HEX (`:LLAAAATT<data>CC`) is a second, unrelated `.hex` dialect** — `src/IntelHexFile.h`, pinned by **`intel_hex_smoke`**. Fed to the WOZMON parser it had no `AAAA:` address, so every digit (byte count, load address, record type, checksum) was written as **data** at whatever address was current — silent, same class as the old `.apl` fall-through. Detection is **structural, never extension-based** (`looksLikeIntelHex` validates the first record's count/type/checksum together), so an Intel HEX named `.txt` loads correctly and a WOZMON dump named `.hex` is untouched; no bundled dump even starts a line with `:`. Once the first record validates POM1 **commits**: a later bad checksum, an unknown record type, or a record past `$FFFF` (the type 02/04 base records are an x86 inheritance) **fails the load loudly** instead of falling back to the WOZMON parser, which would resume writing record headers into RAM. A type 03/05 start record is the Intel-HEX equivalent of WOZMON's trailing `AAAAR`; a missing type-01 EOF only warns.
- **A `.TUR` load is self-checking**: POM1 injects RAM directly, so the `$0100` receiver is written but never executed; the file's last run address is its **CRC-CCITT checker**, which re-verifies the injected image on the emulated 6502 and jumps to the program on match / prints `EE` on mismatch. `hex_dump_turbotype_smoke` runs a real `.TUR` (`tests/fixtures/15puzzle.tur`) and asserts the game's banner appears — no golden byte array needed.
- **Which extensions reach `loadHexDump` is `pom1::isHexDumpPath` in `src/HexDumpFile.h`** — `.txt` `.hex` `.apl` `.mon` `.tur`, one list, four call sites (`CliDispatcher::runLoad`, the Load/Save Memory native filters + the ImGui fallback browser's directory listing in `MainWindow_FileDialogs.cpp`, `Pom1BenchHost::targetForPath`). `.apl` is Uncle Bernie's canonical Apple-1 name for a WOZMON-keystroke file; before the list existed, `--load 0280:prog.apl` fell through to `loadBinary` and wrote the file's **ASCII text** into RAM with no error. Bundled programs keep their `*.apl.txt` double extension (plain-text tooling + pinned test paths). Pinned by `hex_dump_extension_smoke`. `CodeBench.cpp` repeats the extensions literally on purpose (portable module, no POM1 headers).
- **A load warns when a plugged card answers inside it — and never unplugs one for that.** `src/CardShadowing.h` is pure policy (`card_shadowing_smoke`, links nothing); `Memory::loadBinary`/`loadHexDump` call it, so the GUI's Load Memory, `--load` and the control channel's `load` verb share one warning. What it is FOR: `software/Graphic TMS9918/TMS_Logo_16k.txt` spans `$0280-$2D00`, and on the P-LAB Multiplexing Fantasy preset the A1-IO RTC's 65C22 answers at `$2000-$200F` — sixteen bytes in the middle of the program. LOGO's rotation words work; the first word that DRAWS runs to `PC=$0000`. The machine is right (Parmigiani's one-board rule, deliberately broken by that preset) and the user had no way to see it: the load reported success and the program died later, elsewhere. **The discriminator is `CardCapability::Video`, and it is why this reports instead of evicting**: `evictStorageCards` can safely unplug microSD/CFFA1 before a graphics load because their windows only ever shadow, but on a GEN2 machine the framebuffer IS `$2000-$3FFF` and an HGR picture loaded there is the point of the card. A rule that cannot tell "this card shadows my code" from "this card is what my data is for" must not act on the difference. Video cards are therefore skipped whole — including GEN2's `$C200-$C7FF` soft switches, a corner nobody loads a program into. The candidates come from `Memory::cardSlots()`, never a second table, and the message names the card by its registry `uiLabel` so it matches the Hardware menu entry to untick.
- **`--tape` / `--save-tape` are consumed on BOTH paths now, and were not.** The GUI takes them in `finalizeDeferredCardChanges()` (preload) and `~MainWindow_ImGui` (flush); `runHeadless` did neither, so `--headless --tape x` ran with an empty deck and `--headless --save-tape y` recorded a whole cassette and then dropped it — silently, with nothing in the log to say why. The headless driver now preloads **before** the phase-C verbs (same order as the GUI, so a `--load`/`--run` that expects a tape finds one) and flushes on **all three** of its exits: the frame-dump return, the `--exit-after-cycles` return, and the signal wait. `aci_cassette_roundtrip` is what found this and what pins it.
- **A tape that is IN but not ROLLING now says so.** `readTapeInput()` counts consecutive `$C081` polls made while a tape is loaded and the deck is stopped, and warns ONCE past 20 000 (~0.2 s of the ACI's tight `BIT`/`BPL` loop — high enough that a program probing the port once cannot trip it). The failure it names is silent otherwise: `C500R` then `RX RX` on the Extended ACI, with the tape loaded through **File ▸ Load Tape — which loads and does NOT press PLAY, unlike the CLI's `--tape`** — leaves the CPU polling in `$C1xx` forever, printing nothing, looking broken. POM1 knows all three facts at that exact point (something is reading `$C081`, a tape is in, the deck is stopped), which is the whole reason the warning is possible. Pinned by `tools/test_aci_telnet.py` scenario D, including that it does NOT fire on the `--tape` path or with an empty deck — a warning that cried on correct usage would be worse than none.
- **The DevBench's TMS auto-link reads CODE, not comments.** For a pasted source with no sketch context, `Pom1BenchHost` scans for known symbols and pulls the matching `dev/lib/tms9918` module in; a symbol defined locally is skipped so a self-contained sketch keeps linking alone. Both tests run on a COMMENT-STRIPPED copy, and "defined locally" means **a label starting a line**. Reading the raw text made a comment decide the link: `TMS_RogueDiag.asm` says `; … same init path as Rogue (lib init_vdp_g1: 8 Mode-1 …`, the `sym + ":"` probe found that colon, concluded the symbol was local, and dropped `tms9918m1.asm` — taking `init_vdp_g1`, `vdp_set_write`, `vdp_hi` and `vdp_lo` down with it, as four `ld65` unresolved externals. The table also gained the VDP access primitives themselves, which were missing entirely: a program that points the chip at VRAM without calling either init used to link nothing. `sketch_manifests_sync` now asserts the contract — for every sketch on the auto-link path, each imported symbol must be reachable from the modules that table would select.
- **ACI TAPE OUT vs bundled cassette** — `cassettes/WOZ_talk.mp3` is preloaded only when the **POM1 Multiplexing Fantasy (2026)** preset is applied (last preset index); Integer-BASIC cassette presets load `BASIC.aci` instead. While a stream-mode tape is inserted, live `$C0xx` toggles (`$C030` chiptune in GEN2 *A-1-CrazyCycle*) stay silent because `CassetteDevice::fillAudioBuffer()` never mixes the pulse queue. DevBench Run auto-ejects on ACI presets without the Integer-BASIC program tape.
- macOS: `pom1_macos_provision_user_data_dir()` creates `~/Library/Application Support/POM1/` with symlinks for read-only dirs + seeded `sdcard/`/`cfcard/`/`ini/` then chdirs there. Refreshed each launch (handles Gatekeeper App Translocation + `/Applications` drag-installs).
